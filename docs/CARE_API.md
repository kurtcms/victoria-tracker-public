# Care command API

Endpoint: `POST /functions/v1/care-command` (gateway JWT verification enabled). Deploy the matching functions from this release with `verify_jwt=true`, including the legacy `record-event` endpoint. Headers are the same public apikey and signed-in user Bearer JWT used by record-event. No service key is accepted by the app. JSON body is at most 8 KiB; text at most 1,000 UTF-16 code units.

Common fields: request_id UUID, reference_at UTC instant, time_zone IANA name, utc_offset_seconds integer bounded to ±14h, zone_offsets array of 1–16 `{from:UTC,seconds:integer}` entries covering the preceding 366 days in ascending order, and source (`siri`, `text`, `manual`). The final transition offset must match utc_offset_seconds. Capture once and reuse the exact command for retries. Hashing canonicalizes object key order and UUID casing; changing time/name context is a different command.

Modes:

- text: mode="text", text description, optional child_id for app context. English, Cantonese and code-switching are interpreted through a finite conversation schema. With one baby, pronouns may resolve to that profile. With multiple babies the text itself must name exactly one profile; a selected child_id does not satisfy this rule. The model’s extracted name must agree with the literal authorized name. No selected child is attached to Siri input.
- action: mode="action", source="manual", explicit child_id, action and typed payload. Actions are record, sleep_start, sleep_end, sleep_interval, milestone, propose_feeding and propose_edit. Unknown keys are rejected. Ordinary record payloads retain the legacy feeding/diaper/weight shape and explicit unrelated nulls; weight adds its local measurement_date. Sleep uses occurred_at and optional ended_at. Milestones use title, optional note, occurred_on, date_precision, is_first and optional guide_id. Guide IDs identify explicit curated observations; one active row per child/guide ID is allowed and matching free-text titles are not reused. Feeding proposals use correction_kind (leftover/total), amount_ml and optional target_id; omitted target means the latest unambiguous feeding within six hours. Generic edit proposals bind target_type, target_id, expected_revision, void and applicable replacement fields.
- confirm: mode="confirm", explicit child_id, proposal_id and confirmed Boolean. It never invokes OpenAI. A fresh transport request UUID identifies this decision; uncertain retries reuse that UUID and the exact original command. The proposal itself is already bound to actor, target and revision. Optional language="en"/"yue" preserves the proposal’s reply language. Older bodies omit this key and retain their original hash.

HTTP 200 statuses:

- recorded: event_id, child_id and server-authored message after transactional persistence. Multi-event results also include event_ids (1–5 distinct UUIDs); clients require child_id and genuine recorded IDs for isPersisted. A replay adds replayed=true and neutral wording about current details. Confirmed deletion replies name the child and record (for example, “Deleted Victoria’s wet diaper record.”); the wording patch was regression-tested and deployed, without another aloud test.
- answered: child_id, server-authored message and structured details read from authorized database records. This is not a save; it creates no care rows, proposals or receipts.
- needs_confirmation: proposal_id, child_id and a before/after message. The actual record is unchanged. App/Siri must request approval before sending confirmed=true. Cancel/silence never means approval.
- needs_clarification: a request for a new complete named description or missing information; no partial event.
- rejected: informative unsaved/unchanged outcome, including future events, expiry/staleness and interpretation failure. Provider errors/raw model explanations are not returned.

HTTP errors preserve the pending command when the outcome is uncertain. 401 requires sign-in, 403 rejects anonymous sessions, 404 hides inaccessible targets, 409 detects conflicting request IDs, 413/415 reject malformed transport, 422 rejects invalid manual data, 429 limits extraction attempts, and 503 means persistence/access could not be confirmed. A failed write is never relabelled as a definite unsaved interpretation failure.

Structured extraction uses a strict root `{interpretation: ...}` wrapper with operation-specific alternatives and closed action/name/value/time fields. Unrelated fields are forced null; compatibility handling normalizes only neutral defaults, while meaningful conflicting fields still clarify. Grounding and separate confirmation remain required. Absolute clock times are returned as local `absolute_local` / `end_absolute_local` values without a suffix; deterministic code resolves phone-captured offsets. DST overlaps/gaps ask for clarification. Supported questions route only to query operations; negations, examples and hypotheticals do not create events. The model may request only the finite validated action set and cannot execute SQL.

## Additional validation

Extracted feeding/weight/correction quantities must agree with numeric or English-word amounts/units in the supplied text. Common mL letter forms and `mil` are recognized, including corrections; `milk` and `million` are not units. Cantonese full numbers, 毫升 and 公斤/千克 are supported. Shortened 一百八/兩百五 are ambiguous and clarify; use 一百八十 for 180 or 一百零八 for 108. Ounces/安士 are unsupported. Ambiguity clarifies; whole-bottle leftover needs an explicit consumed-total correction. Old unsafe zero proposals cannot apply.

Date-only weight extraction uses time_kind=date, absolute_local=YYYY-MM-DD and other time fields null. The payload includes measurement_date and an internal occurred_at day anchor. Other event types cannot use date-only time. Common explicit English/ISO/Chinese calendar dates must agree with interpreted weight/milestone dates. Milestone titles/notes must be extractively grounded in the submitted words. This is not a complete date parser or a repair of Siri transcription.

## Conversation RPC

The handler maps existing manual/confirmation modes to `execute_care_conversation` operation `action`, with `{action,payload}`. Text maps to one of these finite operations:

- `batch`: `{actions:[{action,payload}]}`, one to five new record/sleep/milestone actions for one baby. The outer request UUID/hash remain stable; deterministic inner IDs are derived from the outer ID and action position. Validation or persistence failure in any part rolls back every part. Queries and edits cannot be mixed into writes.
- `correct`: `{selector:{kind,diaper_kind?,title?,expected_volume_ml?},changes:{...},remove:boolean}`. Kind is feeding, diaper, weight, sleep or milestone. Only the latest qualifying record is supported; tied/not-found targets clarify. A feeding “from 30 to 80 mil” must match the current 30 before proposing 80. Changes preserve unspecified fields and bind the exact target/revision; edits and removals always require a separate confirmation. Ordinary spoken local clock edits or earlier/nth selection clarify; select those records in the app.
- `query`: `{kind,day}`. Kinds are `last_feeding`, `day_summary`, `wet_count`, `dirty_count`, `has_dirty`, `sleep_total`, `last_weight`, `last_milestone` and `last_diaper`. Day is a phone-local ISO date or null for all-time latest queries. Day totals default to the captured phone day; supported explicit dates include today/yesterday. Multi-day windows, medical advice and unsupported metrics clarify. Captured phone offset transitions determine boundaries, mixed diapers count in both categories, and sleep clips to the day and request reference. Latest weight uses measurement_date. Replies distinguish no recorded latest item from recorded zero day totals.

RPC arguments carry the existing child/request/hash/reference/source/timezone fields plus `p_operation`, finite `p_payload` and optional `p_language` (`en`/`yue`, default `en`). Responses include language; static formatters use RPC facts rather than model-generated totals or translations. Unsupported or ungrounded explicit clocks/dates clarify rather than silently defaulting to now.

The additive `202611140001_voice_care.sql` migration introduces this RPC and optional milestone guide IDs. The original three migrations, `execute_care_command` and legacy endpoint remain unchanged for older clients/pending requests. For another project, deploy the migration before the new `care-command` function; `record-event` needs no new deployment for build 14. Apply all five migrations to your own project, then keep them immutable.

## Build 15 query additions

Build 15 adds `last_sleep_start`, `last_sleep_end` and `care_report` to the finite query kinds. Sleep queries return the latest recorded start or wake, optionally within a supported day. `care_report` defaults to phone-local today and combines day totals with the latest feeding and recorded sleep state as of the request; a historical report bounds those facts to that day’s end. It remains read-only with `answered` status.

Before model interpretation, an authenticated, whole-request English grammar recognizes common dirty-diaper/milk-total/sleep-start/wake/status-report/care-report forms (examples in [Siri](SIRI.md#build-15-query-examples)). It cannot consume mixed write clauses or bypass child/name/time validation. Other supported wording still uses finite model interpretation. The six English examples passed physical checks with unchanged care snapshots; Cantonese query replies retain automated coverage only.

Applied migration `202611150001_care_queries.sql` moves the existing implementation to private `execute_care_conversation_v14`, revokes application-role access to it, and creates a public `execute_care_conversation` wrapper with the same signature. Existing operations delegate to the private implementation; new reads reuse its authorization and captured-time checks. This fifth migration was applied before the corresponding function deployment on November 15, 2026; the original four migration files remain unchanged. All 12 hosted postflight checks passed, including the private-RPC access boundary.

## Legacy endpoint

`POST /functions/v1/record-event` remains for older pending entries and shares domain validators with the current handler. It requires the same headers and authenticated-family checks. Its closed body contains request_id, child_id, reference_at, source, locale=en, mode=text/manual, optional time_zone and text or event. Manual events specify event_type, occurred_at, volume_ml, diaper_kind and weight_kg with unrelated fields null. New clients retain absent timezone fields when replaying older requests to preserve hashes.

It returns recorded with a persisted event row, replayed flag and server-authored message, or needs_clarification/rejected without saving. Future/unsupported/interpretation-unavailable outcomes have informative static messages. Uncertain writes remain errors requiring the original pending ID. Limits are the same 8 KiB body/1,000-character text; source is siri/text/manual, feeding up to 2,000 mL (two decimals), weight up to 100 kg (three decimals), diapers wet/dirty/mixed. These are integrity bounds, not clinical guidance. Both functions remain deployed with verify_jwt=true.

Milk-only questions use the extraction kind `milk_total`. The Edge Function reads the existing authorized `day_summary` totals and renders only `feeding_ml`; full summaries and care reports retain their own replies. Whole-number amounts omit trailing decimal zeroes, and meaningful fractions are preserved. This response-formatting change needs no additional migration.

Care/status reports use time-only feeding and sleep detail labels when the fact falls on the report day. Earlier-day facts retain their date. Formatting uses the RPC’s captured-phone local display time; it never reinterprets it in the Edge Function’s timezone. English clocks use AM/PM; Cantonese clocks retain 24-hour times.
